## Part A — contract and data enforcement

Migration: `supabase/migrations/20261020084510_section_visibility.sql` (generated by CLI).

- New table `portfolio_section_visibility`: primary key `(portfolio_id, section)`, portfolio FK with ON DELETE CASCADE, `visible boolean NOT NULL DEFAULT true`.
- Exactly six allowed stable IDs: preface/toc/profile/education/activity/certificate. Cover has no permissible override row, so cannot be disabled by direct SQL/API. Unknown/empty/null IDs and null/invalid boolean values are rejected by data constraints.
- Absence of a row means visible after a **successful** read; old portfolios need no destructive backfill. Table creation does not change content, selections, images, portfolio title/template/colors or accounts.
- RLS policies separately allow SELECT/INSERT/UPDATE only where the referenced portfolio is owned by auth.uid(). UPDATE checks both old/new ownership. Revoke PUBLIC/anon/authenticated table privileges first; grant authenticated only SELECT/INSERT/UPDATE. No DELETE grant and no new SECURITY DEFINER function; existing policies/settings are unchanged.
- Each save upserts exactly one `(portfolio_id, section, visible)` key. Different-section writes cannot overwrite a whole stale map or unrelated portfolio fields. Same-section concurrent writes are last committed write wins; no revision/conflict framework or realtime tab sync is claimed. Other-tab changes appear after reload, not silently merged into a local draft.
- `section-visibility.ts` separates display IDs (including toc) from six form sections. Runtime validation accepts only successful row arrays with known sections/boolean values; missing/null/malformed/duplicate payloads fail instead of becoming all-on. TOC preference remains true even if all content sections are hidden, while showContents returns false until content returns.
