# แผนทดสอบระบบแฟ้มสะสมผลงานฉบับเป้าหมายเต็มรูปแบบ

ฉบับ 1.0 — 14 ตุลาคม 2026 (UTC)

## วัตถุประสงค์และสถานะ

ทดสอบระบบเมื่อพัฒนาครบตาม PRD, ARCHITECTURE, DESIGN_SYSTEM และ AGENTS ฉบับ 1.1 แผนนี้ครอบคลุมพฤติกรรมที่ต้องมี แม้โค้ดปัจจุบันยังไม่มี รายงานสถานะโค้ดอยู่ใน [IMPLEMENTATION_AUDIT.md](IMPLEMENTATION_AUDIT.md)

**ทุกเคสเริ่มสถานะ NOT_RUN ยังไม่มี PASS/FAIL จากการรันจริง** สิ่งที่ระบุในคอลัมน์ผลคาดหวังคือเงื่อนไขรับงาน ไม่ใช่ผลการทดสอบในรอบนี้ เอกสารนี้เป็น test specification ไม่ใช่ชุด automated tests ที่รันได้ทันที

P0 = ข้อมูล/สิทธิ์/เส้นทางสำคัญหรือเกณฑ์รับงานหลัก; P1 = ความครบถ้วนของเนื้อหาและ UX ไม่ใช่สิทธิ์ให้ข้ามข้อกำหนด

## สภาพแวดล้อมและข้อมูลทดสอบ

- ใช้ staging ที่ได้รับอนุญาต แยกจากข้อมูลใช้งานจริง มี schema/migration/Auth/Storage policies ตรงรุ่นที่จะปล่อย บันทึก commit และวันเวลา
- สร้างบัญชี A/B แยกอีเมลที่ตรวจรับข้อความได้ ห้ามใช้ข้อมูลนักเรียนจริง A มี P1/P2 และ P3 เป็นสำเนา; B มีข้อมูลชื่อเหมือนกันเพื่อจับการปะปน
- คลัง A: การศึกษาอย่างน้อย 2 รายการ (มี GPAX และไม่มีโลโก้), กิจกรรม A/B/C อย่างน้อยหนึ่งรายการมีภาพ 4 รูป, เกียรติบัตรมี 2 รูป; มีรายการชื่ออย่างเดียวและ Tags ส่วนตัว
- รูป: ภาพแนวตั้ง/นอน/จัตุรัส, เกียรติบัตรที่ตัวอักษรเล็ก, JPEG/PNG/WebP, ภาพเสีย, URL โหลดล้มเหลว; ใช้ภาพที่ได้รับอนุญาต
- เนื้อหา: ไทยหลายย่อหน้า อังกฤษ URL ยาว อักขระพิเศษ ค่าว่าง ข้อความเกินหนึ่งหน้า และ fixture ที่สร้างได้ 11/25 หน้า
- ใช้ข้อมูลตั้งต้นใหม่ต่อเคส หรือ restore fixture ก่อนรัน เพื่อให้กรณีลบ/แก้/รับอัปเดตไม่ทำให้เคสอื่นผิดโดยไม่เกี่ยวข้อง
- การทดสอบ boundary bytes ใช้ stub ที่ระดับผล export เพื่อคุมขนาดแน่นอน แล้วแยกรัน PDF จริงขนาดใหญ่ตรวจความคมชัด ห้ามนับ stub ว่าผ่านคุณภาพภาพจริง
- สามเทมเพลต × ทุกหมวด × รูป 0–4/0–2 × สี × visibility ต้องครอบคลุม โดยเฉพาะเคส LAY/TPL/PDF ให้รันครบทั้งสามแบบ
- เครื่องทดสอบ: desktop 1366×768 และ 1440×900; mobile กว้าง 360/390 CSS px ทั้งแนวตั้ง/นอน ใช้ emulation ช่วยตรวจแต่ต้องมีโทรศัพท์จริงในรอบรับงาน

## วิธีรันและบันทึกผล

1. บันทึก commit, schema version, config ที่ไม่ลับ, browser/OS, fixture และเวลาเริ่ม
2. เตรียมเงื่อนไขตาม fixture และเคส แยกการรัน UI, API/DB, mock และระบบจริง
3. ทำตามขั้นตอน เก็บ actual result, screenshot/video/network ที่ลบข้อมูลลับแล้ว และไฟล์ PDF ที่เกี่ยวข้อง
4. กำหนด PASS เมื่อครบผลคาดหวัง; FAIL เมื่อพฤติกรรมผิด; BLOCKED เมื่อสภาพแวดล้อมไม่พร้อม; NOT_RUN เมื่อยังไม่รัน ไม่แปลง BLOCKED เป็น PASS
5. ถ้าพบพฤติกรรมที่ยังไม่ตกลง ให้บันทึกคำถาม ไม่เดาว่าเป็นบั๊กหรือผ่าน เช่น นโยบายวันเกิด 29 ก.พ. และ UX แก้ conflict สองแท็บ

## สถานการณ์ End-to-end สำหรับรับงาน

- **E2E-A เส้นทางนักเรียนใหม่:** สมัคร → เก็บการศึกษา/กิจกรรม/เกียรติบัตร → สร้างชื่อพอร์ต → เลือกแบบ → กรอกหมวดพับขยาย → เลือกรายการและรูป → เลือกสองสี → รอ saved → ตรวจสารบัญ/เลขหน้า → ดาวน์โหลด → เปิด PDF อิสระ → เปิดแก้บนมือถือ ข้อมูลต้องตรงกันตลอดเส้นทาง
- **E2E-B หลายพอร์ตและ snapshot:** P1/P2 ใช้ข้อมูลคลังเดียวกันแต่เลือกภาพต่างกัน → แก้ GPAX/ภาพในคลัง → P1 รับ update / P2 คงเดิม → ทำสำเนา P2 → ลบทั้งรายการจากคลังหลังดูผลกระทบ → ทุกพอร์ตปรับตาม โดย PDF ที่เคยดาวน์โหลดไม่เปลี่ยน
- **E2E-C งานยาวและไฟล์ใหญ่:** ข้อมูลยาว 25 หน้าและภาพละเอียด → สลับครบสามแบบ → ปิด/เปิดหมวด → ตรวจ TOC และเนื้อหาต่อ → ลดขนาดโดยรักษาคุณภาพ → ทดสอบยกเลิก/ยืนยันไฟล์ถึง 10 MB → ไม่มีหน้าหาย
- **E2E-D เครือข่ายและสิทธิ์:** เริ่มแก้ P1 → offline → สลับหมวด/preview → reconnect/retry → response เก่าตอบช้า → เปลี่ยนพอร์ต/บัญชี → ตรวจข้อมูลล่าสุดและยืนยันว่า B อ่านข้อมูล A ไม่ได้

บันทึกผล E2E แยกจากเคสย่อย การผ่านเส้นทางหนึ่งไม่ใช้แทนเคสสิทธิ์/ขอบเขตทั้งหมด

## ข้อเสนอด้านคุณภาพที่ต้องระบุให้ชัดก่อนรับงาน

- ตรวจความคมชัดภาพด้วยคนและเก็บ PDF ตัวอย่างที่ยอมรับร่วมกัน ไม่มีตัวเลข compression ที่รับรองว่าอ่านได้เสมอ
- บันทึกเวลาโหลด บันทึก และ export กับจำนวนหน้า/รูปและรุ่นเครื่อง ยังไม่กำหนด SLA วินาทีหรือเพดาน storage ใหม่แทนเจ้าของโครงการ
- ขนาดไฟล์อัปโหลดต่อรูป/ชนิดที่รองรับให้ยึดข้อกำหนดที่รับรองก่อนทดสอบ boundary; โค้ดเดิมมี 5 MB ต่อรูป แต่ไม่เท่ากับเป้าหมาย PDF 10 MB
- ทดสอบอ่าน label/focus และความชัดของข้อความเป็นเกณฑ์ใช้งาน ไม่อ้างว่าได้รับการรับรองมาตรฐาน accessibility ทั้งระบบจากเคสไม่กี่ข้อ
- การไม่มีเพดานหน้าหมายถึงไม่จำกัดเลขหน้าที่ 10 ในผลิตภัณฑ์ ไม่รับรองอุปกรณ์สามารถประมวลผลข้อมูลขนาดอนันต์; กรณีทรัพยากรไม่พอต้องมี error ที่กู้คืนได้

## เกณฑ์ออกจากรอบทดสอบ

- AC-01 ถึง AC-20 ผ่านบน build ที่จะส่งมอบ และเคสตามข้อกำหนดทั้งหมดมีผล/หลักฐานตรวจย้อนกลับได้
- ไม่มีข้อผิดพลาดค้างที่ทำข้อมูลหาย ข้ามสิทธิ์ สร้าง PDF ขาดหน้า หรือผิด flow หลัก; ข้อผิดพลาดอื่นต้องแก้หรือได้รับการยอมรับเป็นข้อยกเว้นโดยระบุผู้รับรอง
- ตรวจ integration กับ Supabase/email/Storage จริงและมือถือจริงแล้ว ไม่ใช้ mock ทดแทน
- migration มีการสำรวจผลกระทบ สำรอง และวิธีกู้คืนที่ตรวจได้ โดยเฉพาะข้อมูลทดลองเกินเพดานภาพ
- บันทึกข้อจำกัด/คำถามที่ยังเปิดอยู่ และ rerun เคสที่กระทบหลังแก้ ไม่สรุประบบสมบูรณ์ขณะที่ยัง BLOCKED

## คำสั่งสำหรับรอบพัฒนา

รันจาก checkout จริงที่ติดตั้ง dependency ตาม lockfile และตั้งค่า environment ที่ได้รับอนุญาต:

```bash
npm ci
npm run lint
npm test
npm run build
npm run test:e2e
```

อ่าน setup ใน playwright.config.ts ก่อนรัน: ชุดปัจจุบันใช้ mock Supabase และ production server ต้องสร้าง build ด้วย config สำหรับ mock ที่ตรงกันใน checkout ทดสอบแยก ห้ามชี้ integration ไป production โดยไม่ตั้งใจ คำสั่งเหล่านี้ **ยังไม่ได้รันในรอบจัดทำเอกสารนี้**

จำนวนเคสย่อยทั้งหมด: **100 เคส** และ E2E สำหรับรับงาน 4 เส้นทาง ทุกเคสเริ่ม NOT_RUN
